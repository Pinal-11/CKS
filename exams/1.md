## Q1 — AppArmor + Least-Privilege Service Account

### Task
A pod in the `omni` namespace has more permissions than it needs and exposes an internal site (`/usr/share/nginx/html/internal`) publicly.

**Fix requirements:**
1. Restrict access to the internal site using the AppArmor profile at `/etc/apparmor.d/frontend`.
2. Re-create the pod using the **least-privileged** service account in `omni` (excluding `default`).
3. Delete the other **unused** service accounts (excluding `default`).
4. Do **not** create a new service account or use `default`.

### Solution

**Step 1 — Load the AppArmor profile** (on the controlplane node):

```bash
apparmor_parser -q /etc/apparmor.d/frontend
```

> The profile name is `restricted-frontend` (check inside the file).

Verify it loaded:

```bash
aa-status | grep restricted-frontend
#    restricted-frontend
```

**Step 2 — Identify least-privileged SA**
Inspect Roles/RoleBindings for each SA in `omni`. `frontend-default` has the fewest permissions; `fe` and `frontend` have extra grants.

**Step 3 — Recreate the pod**

```yaml
apiVersion: v1
kind: Pod
metadata:
  labels:
    run: nginx
  name: frontend-site
  namespace: omni
spec:
  securityContext:
    appArmorProfile:
      type: Localhost
      localhostProfile: restricted-frontend
  serviceAccountName: frontend-default   # least-privileged SA
  containers:
  - image: nginx:alpine
    name: nginx
    volumeMounts:
    - mountPath: /usr/share/nginx/html
      name: test-volume
  volumes:
  - name: test-volume
    hostPath:
      path: /data/pages
      type: Directory
```

Alternatively, edit in place:

```bash
kubectl edit pod frontend-site -n omni
# saved to /tmp/kubectl-edit-XXXXXXXXXX.yaml
```

Delete the original pod, then apply the corrected manifest.

**Step 4 — Clean up unused service accounts**

```bash
kubectl -n omni delete sa frontend
kubectl -n omni delete sa fe
```

### Grading Checklist
- [ ] Correct service account (`frontend-default`) used
- [ ] Obsolete service accounts deleted
- [ ] Internal site restricted (AppArmor enforced)
- [ ] Pod is running

## Q2 — Extracting & Remounting Secrets

### Task
A pod in the `orion` namespace consumes a secret via an environment variable, `CONNECTOR_PASSWORD`.

1. Extract and decode the secret value → save to `/root/CKS/secrets/CONNECTOR_PASSWORD`.
2. Convert the consumption method: stop using an env var, instead **mount the secret as a read-only volume** at `/mnt/connector/password`.

### Approach

```bash
# Identify the secret name/key backing CONNECTOR_PASSWORD
kubectl get pod <pod> -n orion -o yaml | grep -A5 CONNECTOR_PASSWORD

# Decode it
kubectl get secret <secret-name> -n orion -o jsonpath='{.data.CONNECTOR_PASSWORD}' | base64 -d > /root/CKS/secrets/CONNECTOR_PASSWORD
```

Then edit the pod/deployment to remove the `env.valueFrom.secretKeyRef` and instead add:

```yaml
volumes:
  - name: connector-secret
    secret:
      secretName: <secret-name>
containers:
  - volumeMounts:
      - name: connector-secret
        mountPath: /mnt/connector/password
        readOnly: true
```

> **Key CKS principle:** volume-mounted secrets are generally preferred over env vars — env vars can leak via process listings, crash dumps, and child-process inheritance.

## Q3 — Static Analysis for Credential Exposure

### Task
Review YAML manifests and Dockerfiles under `/opt/course/` for **unwanted credential exposure** (ignore root-user concerns). Record offending filenames in `/opt/course/security-issues.txt`.

### What to look for
- Hard-coded secrets/passwords/API keys/tokens directly in `ENV`, `ARG`, or manifest `env:` fields
- Secrets baked into image layers (e.g., `COPY secrets.txt /app/`, then later `RUN rm secrets.txt` — still present in earlier layer)
- `.git`, `.env`, or credential files copied into build context without `.dockerignore` exclusion
- Secrets passed as build args (`ARG` values persist in image history — check with `docker history`)
- Plaintext credentials mounted via `hostPath` without restriction
- `imagePullSecrets` or kubeconfig files copied into image layers

```bash
grep -rniE "password|secret|token|apikey|api_key" /opt/course/ --include="Dockerfile*"
grep -rniE "password|secret|token|apikey" /opt/course/ --include="*.yaml"
docker history --no-trunc <image>   # to spot secrets baked via build args
```

Write every matching filename into `/opt/course/security-issues.txt`.

## Q4 — Seccomp Profile for a Pod

### Task
Create pod `audit-nginx` (namespace `default`, image `nginx:alpine`) restricted using seccomp profile `audit.json` (provided at `/root/CKS`). Move it into the **default seccomp profiles directory** first.

### Solution

```bash
mkdir -p /var/lib/kubelet/seccomp/profiles
cp /root/CKS/audit.json /var/lib/kubelet/seccomp/profiles/
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: audit-nginx
  namespace: default
spec:
  securityContext:
    seccompProfile:
      type: Localhost
      localhostProfile: profiles/audit.json
  containers:
  - name: nginx
    image: nginx:alpine
```

> **Note:** the default seccomp root is `/var/lib/kubelet/seccomp/`; `localhostProfile` is always relative to that root.

## Q6 — Falco Custom Rule & Alert Routing

### Task
Falco fires: *"File below a known binary directory opened for writing"*. Update the rule so that:

- Priority = `CRITICAL`
- Output format = `File below a known binary directory opened for writing (user_id=%user.uid file_updated=%fd.name command=%proc.cmdline)`
- Alerts logged to `/opt/security_incidents/alerts.log`
- Override via `falco_rules.local.yaml` — **do not edit the default rules file**

### Solution

**1. Enable file output** in `/etc/falco/falco.yaml`:

```yaml
file_output:
  enabled: true
  keep_alive: false
  filename: /opt/security_incidents/alerts.log
```

**2. Override the rule** in `/etc/falco/falco_rules.local.yaml`:

```yaml
- rule: Write below binary dir
  desc: an attempt to write to any file below a set of binary directories
  condition: >
    bin_dir and evt.dir = < and open_write
    and not package_mgmt_procs
    and not exe_running_docker_save
    and not python_running_get_pip
    and not python_running_ms_oms
    and not user_known_write_below_binary_dir_activities
  output: >
    File below a known binary directory opened for writing (user_id=%user.uid file_updated=%fd.name command=%proc.cmdline)
  priority: CRITICAL
  tags: [filesystem, mitre_persistence]
```

**3. Hot-reload Falco:**

```bash
kill -1 $(cat /var/run/falco.pid)
# or
systemctl restart falco
```

> Overriding a rule by **name** in the `.local.yaml` file replaces the original definition without touching `falco_rules.yaml`. Give it up to a minute before checking the new log path.

## Q7 — SBOM Generation (SPDX)

### Task
Deployment `fruits` (namespace `salad`) has containers `apple`, `banana`, `kiwi`. One has `curl` installed.

1. Identify which container has `curl`.
2. Generate an SPDX JSON SBOM for that container's image using its tarball in `/root/ImageTarballs/`.
3. Save SBOM → `~/bugged-fruit.spdx`; save container name → `~/bugged-container.txt`.

### Solution

```bash
kubectl get deployments -n salad
kubectl exec -n salad fruits-<hash> -c apple  -- apk info | grep curl && echo apple  > ~/bugged-container.txt
kubectl exec -n salad fruits-<hash> -c banana -- apk info | grep curl && echo banana > ~/bugged-container.txt
kubectl exec -n salad fruits-<hash> -c kiwi   -- apk info | grep curl && echo kiwi   > ~/bugged-container.txt

kubectl describe pod fruits-<hash> -n salad   # find the image name for that container

bom generate --image-archive /root/ImageTarballs/<image_name>.tar \
  --format json \
  --output ~/bugged-fruit.spdx
```

## Q8 — ServiceAccount Automount & Projected Token

### Task
1. Create ServiceAccount `bot-sa` in namespace `automated` — **must not** auto-mount its token.
2. Point deployment `sweeper` (same namespace) at `bot-sa`.
3. Manually mount the SA token as a **projected volume**. Don't change any other deployment fields.

### Solution

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: bot-sa
  namespace: automated
automountServiceAccountToken: false
```

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sweeper
  namespace: automated
spec:
  replicas: 1
  selector:
    matchLabels:
      app: sweeper
  template:
    metadata:
      labels:
        app: sweeper
    spec:
      serviceAccountName: bot-sa
      automountServiceAccountToken: false
      containers:
        - name: sweeper
          image: busybox:1.36
          command: ["sleep", "3600"]
          volumeMounts:
            - name: sa-token
              mountPath: /var/run/secrets/tokens
              readOnly: true
      volumes:
        - name: sa-token
          projected:
            sources:
              - serviceAccountToken:
                  path: bot-token
                  expirationSeconds: 3600
                  audience: default
```

Token ends up at `/var/run/secrets/tokens/bot-token`.

## Q9 — Pod Security Admission (PSA) Troubleshooting

### Task
Deployment `web-server` (namespace `restricted`) won't reach Running. Diagnose and fix — **without** changing namespace labels or the container image.

### Solution

```bash
kubectl get deployments -n restricted          # READY 0/1
kubectl describe deployment web-server -n restricted
kubectl describe replicaset -n restricted      # check Events
```

Events reveal PSA (`restricted` level) is rejecting the pod:

```
violates PodSecurity "restricted:latest":
  allowPrivilegeEscalation != false
  unrestricted capabilities
  runAsNonRoot != true
  runAsUser=0
  seccompProfile not set
```

Confirm enforcement:

```bash
kubectl get namespace restricted --show-labels
# pod-security.kubernetes.io/enforce=restricted
```

Fix the deployment's `securityContext`:

```bash
kubectl edit deployment web-server -n restricted
```

```yaml
securityContext:
  allowPrivilegeEscalation: false
  capabilities:
    drop:
    - ALL
  runAsNonRoot: true
  seccompProfile:
    type: RuntimeDefault
  # remove runAsUser: 0 entirely
```

## Q10 — NetworkPolicy with Namespace & Pod Selectors

### Task
Allow ingress to `web-app` (namespace `products`) from:
- `product-db` pods in namespace `database`
- **all** traffic from namespace `payments`

Use existing labels; name the policy `allow-traffic-to-products`.

### Solution

```bash
kubectl get pods -n products --show-labels     # app=web-app
kubectl get pods -n database --show-labels     # app=database
kubectl get ns database payments --show-labels # kubernetes.io/metadata.name=<ns>
```

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-traffic-to-products
  namespace: products
spec:
  podSelector:
    matchLabels:
      app: web-app
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: database
      podSelector:
        matchLabels:
          app: database
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: payments
```

> **Critical gotcha:** two selectors inside **one** `from` list-item (combined with `podSelector` + `namespaceSelector` under the *same dash*) = AND. Two separate dash-items = OR. Here, `database`+`app=database` are AND'd (specific pod in specific ns), while `payments` is its own OR'd entry (whole namespace).

## Q11 — Container SecurityContext Hardening

### Task
Edit deployment `gamma` (namespace `galaxy`) so **all** containers:
- Run as UID `1001`
- Disallow privilege escalation
- Use a read-only root filesystem

### Solution

```bash
kubectl edit deployment gamma -n galaxy
```

Add per-container (these are **container-level**, not pod-level, fields):

```yaml
securityContext:
  runAsUser: 1001
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
```

> Remember: `allowPrivilegeEscalation` and `readOnlyRootFilesystem` only exist at the **container** `securityContext` — setting them at the pod level has no effect.

## Q12 — Ingress with TLS Termination

### Task
Expose `rocket-server` (deployment + service, namespace `space`) via Ingress `rocket-ingress`:
- Path `/`
- Host `rocket-server.local`
- TLS via existing secret `rocket-tls`

### Solution

```bash
kubectl describe deployment rocket-server -n space   # find container port
```

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: rocket-ingress
  namespace: space
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - rocket-server.local
      secretName: rocket-tls
  rules:
    - host: rocket-server.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: rocket-server
                port:
                  number: 80
```

```bash
kubectl get svc -n ingress-nginx
echo "<INGRESS-IP> rocket-server.local" | sudo tee -a /etc/hosts
curl -k https://rocket-server.local
```

## Q13 — RBAC Least Privilege Across Namespaces

### Task
User `martin` needs:
- **Full** pod permissions in `dev-a` and `dev-b`
- **Only `get`/`list`** pods in `dev-z`

Current setup over-grants in `dev-z`. Fix it, keeping the same object **names**.

### Solution

Re-create the `dev-z` role with restricted verbs:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: dev-user-access
  namespace: dev-z
rules:
  - apiGroups:
    - ""
    resources:
    - pods
    verbs:
    - get
    - list
```

Leave `dev-a`/`dev-b` roles as-is (already unrestricted, matching the requirement).

## Q14 — Kubernetes Audit Logging

### Task
Enable auditing with base policy `/etc/kubernetes/cluster-policy.yaml`:
- Log path: `/var/log/cluster-audit.log`
- Retention: 10 days, max 10MB/file, max 3 backups
- Policy rules:
  - `delete` on `secrets` in `kube-system` → **Metadata**
  - Deployment changes in `default` → **Request**
  - Everything else → **Metadata**

### Solution

**Policy file:**

```yaml
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages:
  - "RequestReceived"
rules:
  - level: Metadata
    verbs: ["delete"]
    resources:
      - group: ""
        resources: ["secrets"]
    namespaces: ["kube-system"]
  - level: Request
    verbs: ["create", "update", "patch", "delete"]
    resources:
      - group: "apps"
        resources: ["deployments"]
    namespaces: ["default"]
  - level: Metadata
```

**`kube-apiserver.yaml`** — add flags:

```yaml
- --audit-policy-file=/etc/kubernetes/cluster-policy.yaml
- --audit-log-path=/var/log/cluster-audit.log
- --audit-log-maxage=10
- --audit-log-maxbackup=3
- --audit-log-maxsize=10
```

Add matching `volumes` / `volumeMounts` for the policy file and `/var/log`:

```yaml
volumes:
  - name: audit-policy
    hostPath:
      path: /etc/kubernetes/cluster-policy.yaml
      type: File
  - name: varlog
    hostPath:
      path: /var/log
      type: Directory
```

```yaml
volumeMounts:
  - mountPath: /etc/kubernetes/cluster-policy.yaml
    name: audit-policy
    readOnly: true
  - mountPath: /var/log
    name: varlog
```

Verify:

```bash
kubectl get pods -n kube-system   # wait for apiserver to come back healthy
ls -l /var/log/cluster-audit.log
```

> Rule order matters — audit policy rules are evaluated **top-down**, first match wins. That's why the specific `secrets`/`deployments` rules come before the catch-all `Metadata` rule.

## Q15 — ImagePolicyWebhook Admission Controller

### Task
Block any pod using the `:latest` tag cluster-wide via `ImagePolicyWebhook`:
1. Create `/etc/admission-controllers/admission-configuration.yaml`.
2. Point it at the webhook kubeconfig (`/root/CKS/ImagePolicy/admission-kubeconfig.yaml`, mounted at `/etc/admission-controllers/...`).
3. **Fail closed** (reject if webhook is unreachable / on `latest`).
4. Enable the plugin.
5. Fix the existing non-compliant pod `app-0403` in `magnum` (change `:latest` → `:1.27`).

### Solution

**Admission config** (place under `/root/CKS/ImagePolicy/`, since it's mounted at `/etc/admission-controllers`):

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration
plugins:
- name: ImagePolicyWebhook
  configuration:
    imagePolicy:
      kubeConfigFile: /etc/admission-controllers/admission-kubeconfig.yaml
      allowTTL: 50
      denyTTL: 50
      retryBackoff: 500
      defaultAllow: false     # fail closed
```

**Edit `kube-apiserver.yaml`:**

```yaml
- --admission-control-config-file=/etc/admission-controllers/admission-configuration.yaml
- --enable-admission-plugins=NodeRestriction,ImagePolicyWebhook
```

> ⚠️ If the API server becomes unresponsive, restore from `/root/backup/kube-apiserver.yaml` and retry carefully.

**Remediate the existing pod:**

```bash
kubectl get pod app-0403 -n magnum -o yaml > app-0403-fix.yaml
vi app-0403-fix.yaml
# image: gcr.io/google-containers/busybox   →   image: gcr.io/google-containers/busybox:1.27
# strip status/managed fields, resourceVersion, uid, etc.

kubectl delete pod app-0403 -n magnum
kubectl apply -f app-0403-fix.yaml
```

> Admission controllers only intercept **new** API requests — they never retroactively evaluate already-running pods. That's why the old pod must be deleted and recreated to be checked against the new policy.
